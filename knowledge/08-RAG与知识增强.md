# 08 · RAG与知识增强

> 这一篇是整套知识库的"承上启下"：前面讲的都是 Agent 本身，这一篇讲怎么让模型"用上外部的
> 知识库"——这就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**。它也是你下一阶段
> 学习的核心目标。

---

## 一、为什么模型需要"检索增强"

### 1.1 大模型的三个短板

大模型虽然强大，但有三个天生短板：

1. **知识有截止日期**：模型训练完那一刻，它"知道"的世界就定格了，之后发生的新闻它不知道
2. **不知道你的私有数据**：你的公司文档、项目代码、内部知识，它没训练过，自然不知道
3. **会一本正经地编造**：当它不知道答案时，可能编一个看似合理、实则错误的内容（幻觉）

### 1.2 微调 vs RAG

要让模型掌握新知识，有两条路：

| 方案 | 做法 | 缺点 |
| --- | --- | --- |
| 微调（Fine-tuning） | 用新数据继续训练模型，改变模型本身 | 贵、慢、知识更新不灵活 |
| RAG | 检索时把相关资料塞进上下文 | 便宜、灵活、知识随时更新 |

**RAG 的思路不是"改造模型"，而是"喂给它相关资料"**——模型还是那个模型，但在回答前，
先给它找到的参考材料。

### 1.3 RAG 的定义

> **RAG = 先检索（Retrieval）相关资料，再让模型基于这些资料生成（Generation）回答。**

一句话：**"答之前先查资料，再照着资料回答"，而不是让模型凭记忆硬答。**

---

## 二、RAG 的核心流程

RAG 分两个阶段：**离线建库** 和 **在线问答**。

### 2.1 离线阶段：建库（一次性）

```
原始文档（.md / .txt / .pdf）
   ↓ 1. 切块（chunking）
一个个语义片段（chunk）
   ↓ 2. 向量化（embedding）
一堆向量（存在向量库）
```

### 2.2 在线阶段：问答（每次提问）

```
用户提问
   ↓ 1. 把问题向量化
问题的向量
   ↓ 2. 检索（和向量库里的 chunk 算相似度）
最相关的 top-k 个片段
   ↓ 3. 生成（把片段拼进 prompt，让模型照着答）
最终回答
```

> 你现在搭的知识库（knowledge/ 目录下的 11 篇 Markdown），就是"离线阶段"的**原始文档**。
> 下一阶段 RAG 学习时，你会亲手把它切块、向量化、建库。

---

## 三、文档切块（Chunking）

### 3.1 为什么要切块

模型上下文有限，不能把整本书塞进去。而且检索时，我们希望拿到的是**一小段精确相关的内容**，
而不是一整章无关的东西。所以要把长文档切成一个个小片段（chunk）。

### 3.2 切块策略

常见策略有：

- **按固定字符数切**：简单粗暴，比如每 500 字一块，但容易把一句话从中间切断
- **按段落切**：按空行/段落切，比固定字符数好，但段落可能太长或太短
- **按标题（小节）切**：按 `##` 标题切，每块语义相对完整（推荐）
- **滑动窗口 + 重叠**：切块时让相邻块有一部分重叠，避免边界信息丢失

### 3.3 语义完整的重要性

切块的黄金法则是：**每个 chunk 要能"独立读懂"**。如果一个 chunk 的开头是"因此..."，但
"因此"的原因在上一块，那这个 chunk 检索出来后，模型也看不明白。

> 这正是你这份知识库在写作时就"按小节分段、语义独立"的原因——为后续切块检索做准备。

## 四、向量化（Embedding）

### 4.1 什么是 embedding

**Embedding（向量化）** 是把一段文字转换成一个**数字向量**（一串数字）的技术。语义相近的
文字，向量在空间里的位置也相近。

例如（示意）：

```text
"今天天气很好"   → [0.12, 0.83, -0.45, 0.67, ...]
"今天是个晴天"   → [0.13, 0.81, -0.43, 0.66, ...]  ← 和上一句很接近
"苹果发布了新手机" → [-0.71, 0.22, 0.58, -0.31, ...] ← 离得很远
```

### 4.2 为什么能算相似度

向量之间的"距离"（余弦相似度等）衡量了语义的接近程度。把问题和所有 chunk 都向量化后，
只要算"哪个 chunk 的向量离问题的向量最近"，就找到了最相关的内容。

**embedding 模型**就是干这件事的模型，例如 OpenAI 的 `text-embedding` 系列。

---

## 五、检索（Retrieval）

### 5.1 向量检索

把用户问题向量化，然后到向量库里找"最相似"的若干 chunk。检索方式：

- 暴力全量比对（数据少时够用）
- 向量数据库 / 索引（数据多时加速，如 FAISS、Milvus、pgvector）

### 5.2 相似度

常用的相似度计算是**余弦相似度**，结果在 -1 到 1 之间，越接近 1 表示越相似。

### 5.3 top-k

检索通常返回最相关的 **top-k** 个片段（比如 top-3、top-5）。k 太小可能漏掉关键信息，
k 太大又塞不进上下文、还可能引入噪音。需要根据实际情况调。

---

## 六、生成（Generation）

### 6.1 拼接上下文

检索到片段后，把它们和用户问题一起拼进 prompt，让模型"基于资料回答"：

```text
请根据以下资料回答用户问题。如果资料里没有答案，就说"资料中未找到"，不要编造。

【资料】
1. （检索到的 chunk 1）
2. （检索到的 chunk 2）

【用户问题】
{用户的问题}
```

### 6.2 关键：禁止编造

RAG 的 prompt 里必须强调"资料里没有就老实说没有"。否则模型检索不到时，又会退回"凭记忆
编造"，RAG 就白做了。

---

## 七、一个完整的 RAG 例子

用户问："这个项目里，Agent 最多能执行多少轮？"

1. **切块建库**：`02-ReAct循环与工具调用.md` 里的"最大轮次"小节被切成一个 chunk
2. **向量化**：该 chunk 变成向量存入向量库
3. **检索**：把问题向量化，发现这个 chunk 最相关（讲"最大轮次"）
4. **生成**：把该 chunk 拼进 prompt，模型回答："默认最多 12 轮，超过会提前结束"

对比没有 RAG 时：模型可能凭记忆乱猜一个数字，或者干脆说不知道。

---

## 八、常见问题与坑

1. **切块太碎**：检索到的片段语义不完整，模型看不懂
2. **切块太粗**：一块塞进太多无关内容，稀释关键信息
3. **不设 top-k 上限**：检索结果太多，上下文被撑爆
4. **prompt 不强调"禁止编造"**：检索失败时模型又去编
5. **embedding 用错模型**：中英文、领域不同，需要合适的 embedding 模型
6. **向量没存好**：更新文档后没重新向量化，检索到旧内容

## 九、与 Agent 的结合

RAG 和 Agent 不是二选一，而是可以组合：

- **纯 RAG**：提问 → 检索 → 生成，一次到位
- **Agent + RAG**：Agent 把"检索"也当成一个工具，需要查资料时才调用它

你接下来要搭的前端界面，就是"纯 RAG"的形态：提问 → 展示检索片段 + 回答。等 RAG 学完，
还可以再升级成"Agent 把检索当工具用"。

## 十一、小结

- RAG 解决模型"知识过时、不懂私有数据、爱编造"三个短板
- RAG = 检索 + 生成：先查资料，再照着答，而不是凭记忆硬答
- 核心流程：切块 → 向量化 → 建库（离线）；问题向量化 → 检索 top-k → 生成（在线）
- 切块要保证语义完整，检索要控制 top-k，prompt 要禁止编造
- RAG 和 Agent 可以组合，Agent 把"检索"当成一个工具
