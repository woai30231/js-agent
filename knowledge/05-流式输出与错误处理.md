# 05 · 流式输出与错误处理

> 前四篇搭起了 Agent 的骨架。这一篇讲两个"工程硬骨头"：**流式输出**（让回答像打字机一样
> 一个字一个字蹦出来）和**错误处理**（网络出错时怎么超时、怎么重试、怎么分类）。

---

## 一、为什么需要流式输出

### 1.1 非流式的问题

非流式调用是"等模型把整段回答全部生成完，再一次返回"。模型生成一段长回答可能要几十秒，
用户只能干等着，屏幕上什么都没发生，体验很差。

### 1.2 流式的好处

流式输出让模型**边生成边返回**，代码拿到一个 token 就显示一个 token。用户立刻能看到
"模型正在打字"，感知延迟大幅降低。几乎所有聊天产品都做成了流式。

---

## 二、什么是 SSE

### 2.1 定义

**SSE（Server-Sent Events，服务端推送事件）** 是一种让服务器持续向客户端推送数据的协议。
流式输出就是靠 SSE 实现的：服务器不一次性返回，而是持续吐出一个个数据块。

### 2.2 SSE 的数据格式

SSE 的数据流由一行行 `data: ...` 组成，每个事件之间用空行分隔：

```text
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

最后一条 `[DONE]` 表示流结束。

### 2.3 流式返回长什么样

在流式模式下，模型不再是返回一个完整的 message，而是返回一串**增量（delta）**：

- 每个 delta 只包含一小段文字（`delta.content`）
- 或者一小段工具调用参数（`delta.tool_calls`）
- 代码需要把这些增量**拼起来**，还原成完整回答

---

## 三、解析 SSE 流

### 3.1 逐块读取

代码用流式读取响应的 body，把收到的每个 chunk 按 `data:` 行解析出来：

```js
const reader = res.body.getReader();   // 拿到流
const decoder = new TextDecoder();

while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const text = decoder.decode(value, { stream: true });
    // 解析 text 里的 data: 行，提取 delta
}
```

### 3.2 按 index 归并 tool_calls

流式模式下，一个工具调用的 `id`、`name`、`arguments` 可能**分片到达**。比如参数
`{"expression":"1+1"}` 可能被拆成 `{"expr` 和 `ession":"1+1"}` 两段。

所以解析时必须**按 index 归并**，把同一 index 的碎片拼到一起：

```js
// 工具调用分片到达，需要按 index 累积
if (!toolCalls[index]) {
    toolCalls[index] = { id: '', function: { name: '', arguments: '' } };
}
toolCalls[index].id += tc.id ?? '';
toolCalls[index].function.name += tc.function?.name ?? '';
toolCalls[index].function.arguments += tc.function?.arguments ?? '';
```

这是流式解析里最容易出 bug 的地方：**分片没拼全，工具调用就是坏的。**

## 四、超时

### 4.1 为什么需要超时

网络请求可能永远挂起——服务器卡住、网络抖动、DNS 解析失败。如果不设超时，程序就会
一直卡在 `await fetch(...)` 上，用户以为程序死了。

### 4.2 怎么实现

用 `AbortSignal.timeout` 给请求设定一个最长等待时间，超时自动中止：

```js
const res = await fetch(url, {
    method: 'POST',
    // ...
    signal: AbortSignal.timeout(60_000),  // 60 秒超时
});
```

超时后 fetch 会抛出一个 `TimeoutError` 类型的异常，代码可以据此判断"这是超时，可以重试"。

---

## 五、重试与指数退避

### 5.1 哪些错误该重试

不是所有错误都值得重试。重试的典型对象是"**暂时性错误**"：

- 网络抖动、断网重连（TypeError / 网络层错误）
- 服务器过载（5xx 状态码）
- 限流（429）
- 超时

### 5.2 哪些不该重试

**业务性错误**重试也没用，应该直接失败：

- 401（key 错了）——重试一百次也是 key 错
- 400（请求格式错）——重试还是同样的错

**经验**：把"能不能重试"这个判断，直接放进错误对象里，而不是散落在调用处。

### 5.3 指数退避

重试不是"立刻再来一次"，而是**越等越久**，给服务器喘息时间：

```js
function backoffMs(attempt, baseMs) {
    const exponential = Math.min(8000, baseMs * 2 ** attempt); // 500→1000→2000→封顶8s
    return exponential + Math.floor(Math.random() * 250);       // 加随机抖动
}
```

- `2 ** attempt` 是"指数"：每次等待时间翻倍
- 随机抖动是为了避免大量客户端同时重试、再次把服务器打挂（惊群效应）

### 5.4 流式重试的限制

流式输出有个特殊约束：**如果已经吐出了一部分内容，就不能再重试了**。因为重试会重新请求，
用户会看到前面已经显示的文字又重复出现。所以流式通常只允许"还没吐出任何 token 之前"重试。

---

## 六、错误分类

把错误分好类，处理逻辑就清晰了：

| 类型 | 典型表现 | 该不该重试 | 处理 |
| --- | --- | --- | --- |
| 业务错误（4xx） | 401、400、404 | 不该 | 直接抛错，提示用户检查 |
| 服务器错误（5xx） | 500、502、503 | 该 | 指数退避重试 |
| 限流 | 429 | 该 | 尊重 retry-after 或退避重试 |
| 网络错误 | TypeError、断网 | 该 | 指数退避重试 |
| 超时 | TimeoutError | 该 | 指数退避重试 |

把错误统一封装成一个带 `retryable` 标记的类型，重试逻辑就只需要问一句"这错误该不该重试"。

## 八、小结

- 流式输出靠 SSE，模型边生成边返回，体验更好
- SSE 是 `data:` 行 + 空行分隔，最后 `[DONE]` 结束
- 流式的 tool_calls 会分片到达，必须按 index 归并
- 超时用 `AbortSignal.timeout`，防止请求永久挂起
- 重试只针对"暂时性错误"（5xx、限流、超时、网络），业务错误（4xx）不重试
- 指数退避 = 每次等待翻倍 + 随机抖动
- 流式一旦吐了内容就不能重试，避免用户看到重复文字
