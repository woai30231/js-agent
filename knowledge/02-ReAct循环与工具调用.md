# 02 · ReAct循环与工具调用

> 上一篇讲了 Agent 是"LLM + 工具 + 上下文 + 循环"。这一篇深入拆解那个"循环"——它叫 ReAct，
> 是 Agent 能自主完成多步任务的核心机制。

---

## 一、什么是 ReAct

### 1.1 名字的由来

**ReAct** 是 **Reasoning + Acting** 的缩写，直译是"推理 + 行动"。它最早来自 2023 年的一篇论文，
核心主张是：让模型**边思考边行动**，把"想"和"做"交替进行，而不是一口气想完再一次性做完。

### 1.2 核心思想

传统的做法是"模型给一个答案，代码照做"；ReAct 的做法是"模型先想一步，做一步，看看结果，
再想下一步"。这种"边想边做、根据反馈调整"的方式，让模型能处理那些**无法提前预知全貌**的任务。

### 1.3 一个生活类比

想象你让一个助手"帮我订一家好吃的川菜馆"：

- 助手不会凭空报个馆子名，而是先**想**："我得先知道你现在在哪"
- 于是它**行动**：查你的定位
- 拿到位置后它**观察**结果，再**想**："这个区域有 3 家川菜馆，我需要看评分"
- 它再**行动**：查这 3 家的评分
- 最后综合出结论推荐给你

这就是 ReAct：想一步、做一步、看结果、再想。

## 二、ReAct 的三个环节

一个 ReAct 循环，由三个环节反复交替构成：

### 2.1 思考（Thought）

模型根据当前上下文，决定"接下来要做什么"。思考的结果有两种：

- **要调工具**：模型输出一个工具调用指令（调哪个工具、传什么参数）
- **要收尾**：模型觉得信息够了，直接输出最终回答

注意：模型的"思考"不一定显式写出文字，更多时候是通过"是否返回 tool_calls"来体现。

### 2.2 行动（Action）

代码拿到模型的工具调用指令后，**真正去执行**：

- 把 `name` 和 `arguments` 解析出来
- 调用对应的工具处理函数
- 拿到真实结果

这一步是"代码干活"，不是模型干活。模型只负责"点名"，执行靠代码。

### 2.3 观察（Observation）

把工具执行的结果，以特定格式**喂回上下文**，让模型知道"你刚才那步的结果是这个"。
然后回到"思考"，开始下一轮。

```text
思考 → 行动 → 观察 → 思考 → 行动 → 观察 → …… → 最终回答
```

## 三、循环怎么运转

### 3.1 完整流程

```text
┌─────────────────────────────────────────────┐
│ 用户提问                                       │
└───────────────┬─────────────────────────────┘
                ▼
      ┌──────────────────┐
      │ 问模型（含工具清单）│◄──────┐
      └────────┬─────────┘       │
               ▼                 │
      模型返回 tool_calls 吗？     │
         ┌─────┴─────┐           │
        是            否          │
         │             │          │
         ▼             ▼          │
     执行工具      输出最终回答 ────┘
         │            （结束）
         ▼
     把结果喂回上下文
         │
         └────────────────────────┘
```

### 3.2 一个多轮例子

用户问："帮我查一下北京现在几点，然后用 (1+2)*3 验证一下计算器。"

**第 1 轮**
- 模型思考：需要查时间和算数，两个工具都要调
- 模型行动：返回两个 tool_calls —— `get_current_time` 和 `calculator(expression="(1+2)*3")`
- 代码执行：查时间得到 `14:30:00`，计算器得到 `9`
- 观察：把两个结果喂回模型

**第 2 轮**
- 模型思考：两个结果都拿到了，可以回答了
- 模型收尾：输出"现在北京是 14:30:00，(1+2)*3 等于 9"

这个例子体现了两个要点：**一次可以调多个工具**，**结果齐了再收尾**。

## 四、为什么要设最大轮次

### 4.1 防止死循环

如果模型一直觉得自己"还没做完"，就会无限调用工具。最坏情况下，模型可能反复调用同一个
工具、拿到同样的结果、却一直不罢休。**最大轮次（maxTurns）就是安全阀**，到点强制停下。

### 4.2 控制成本

每一轮都要重新把完整上下文发给模型，都会消耗 token。轮次越多，成本越高、延迟越大。
设上限能避免"一个任务烧掉几十轮 token"。

### 4.3 如何选一个合理值

- 简单任务：1~3 轮就够
- 一般任务：5~10 轮比较常见
- 复杂任务：可能到 15~20 轮

经验值：**大多数任务在 12 轮以内能完成**，所以很多项目默认把 maxTurns 设为 12。设太大
是浪费，设太小会让复杂任务中途被掐断。

### 4.4 达到上限后的处理

达到上限时，不应该假装成功，而应该明确告诉用户"任务没做完"：

```js
return '⚠️ 已达到最大轮次限制，任务提前结束。';
```

让用户知道"这是被截断的"，而不是一个看起来完整、其实半截的答案。

## 五、串行 vs 并行执行工具

当模型一轮返回多个工具调用时，代码有两种执行方式：

### 5.1 串行执行

一个接一个执行，前一个完成才执行下一个。

```js
for (const call of assistantMsg.tool_calls) {
    const result = await runTool(call.function.name, call.function.arguments);
    messages.push({ role: 'tool', tool_call_id: call.id, content: result });
}
```

- 优点：逻辑简单，工具之间有依赖时安全
- 缺点：慢，多个独立工具也要排队

### 5.2 并行执行

用 `Promise.all` 同时执行所有工具：

```js
const outcomes = await Promise.all(
    assistantMsg.tool_calls.map((call) => runTool(call.function.name, call.function.arguments))
);
```

- 优点：快，多个独立工具同时跑
- 缺点：工具之间有依赖时不能乱序，需要保证结果和调用一一对应

### 5.3 什么时候该并行

- 工具之间**没有依赖**：并行（例如"查时间"和"算数"互不依赖）
- 工具之间**有依赖**：必须串行（例如"先读文件，再根据文件内容决定下一步"）

一个常见陷阱：并行执行时，结果的**顺序必须和 tool_calls 的顺序一致**，因为回填时靠
`tool_call_id` 对应，一旦错位模型就会张冠李戴。

## 六、工具失败的反馈

### 6.1 错误也是观察

工具执行出错时，不要直接让整个程序崩溃，而是**把错误信息作为观察结果喂回模型**：

```js
try {
    const result = await handler(args);
    return result;
} catch (err) {
    return `工具执行出错：${err.message}`;
}
```

这样模型看到"出错了、错在哪"，就能自己调整策略（换参数、换工具），而不是被一刀切死。

### 6.2 让模型自己调整

比如模型调 `read_file` 读一个不存在的文件，工具返回"文件不存在"：

- 模型可能会调整：换个路径再读一次
- 或者换个工具：先用 `list_files` 看看目录里到底有啥

**把错误当作"另一种有用的信息"**，是 Agent 比普通程序更聪明的地方。

## 七、代码对应关系

本文讲的概念，在你的项目里是这样落地的：

| 概念 | 代码位置 |
| --- | --- |
| ReAct 循环 | `src/agent.js` 的 `runAgent` 里的 `for` 循环 |
| 思考（模型决策） | `chat()` 返回的 `assistantMsg.tool_calls` |
| 行动（执行工具） | `src/tools.js` 的 `runTool` |
| 观察（喂回结果） | `messages.push({ role: 'tool', ... })` |
| 最大轮次 | `src/config.js` 的 `maxTurns`（当前硬编码 12） |
| 错误反馈 | `runTool` 里的 try/catch |

---

## 八、小结

- ReAct = 思考 → 行动 → 观察，三个环节循环往复
- 模型只负责"点名调哪个工具"，真正执行靠代码
- 最大轮次是安全阀，防止死循环、控制成本，默认 12 轮
- 多工具可以串行也可以并行，关键看工具之间有没有依赖
- 工具出错时把错误信息喂回模型，让它自己调整，而不是直接崩
