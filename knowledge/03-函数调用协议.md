# 03 · 函数调用协议

> 上一篇讲了 ReAct 循环的"节奏"。这一篇讲"语言"——模型和代码之间，到底靠什么约定来互相
> 听懂？答案就是**函数调用协议（Function Calling）**。

---

## 一、什么是函数调用

### 1.1 定义

**函数调用**是一种让大模型输出"结构化指令"的机制。模型不直接给一句人话，而是输出一个
结构化的 JSON，里面写着"我要调用哪个函数、传什么参数"。

代码拿到这个 JSON 后，找到对应的函数去执行，再把结果按约定格式还给模型。

### 1.2 为什么需要协议

如果模型只能说人话，那"查一下当前时间"这句话，代码得靠解析自然语言才能理解意图，非常不可靠。
而函数调用让模型的输出是**机器可解析的 JSON**，代码可以精确地、无歧义地执行。

### 1.3 一个类比

函数调用协议就像**给模型发了一张"菜单"**：

- 菜单上写着每道菜的名字（工具名）、食材要求（参数）、做法说明（描述）
- 模型看完菜单，点菜（输出结构化指令）
- 厨房（代码）照着菜单做菜（执行函数）
- 上菜（把结果还给模型）

菜单就是"协议"，双方按它对齐。

---

## 二、tool schema：告诉模型"你有哪些工具"

### 2.1 schema 的结构

在请求里，你会把一份**工具清单**发给模型，每个工具用一段 JSON Schema 描述。基本结构：

```json
{
  "type": "function",
  "function": {
    "name": "get_current_time",
    "description": "获取当前的日期和时间",
    "parameters": {
      "type": "object",
      "properties": {},
      "required": []
    }
  }
}
```

### 2.2 一个带参数的完整示例

以计算器工具为例：

```json
{
  "type": "function",
  "function": {
    "name": "calculator",
    "description": "计算数学表达式，支持 + - * / ( ) 和小数点",
    "parameters": {
      "type": "object",
      "properties": {
        "expression": {
          "type": "string",
          "description": "例如 \"(1+2)*3\""
        }
      },
      "required": ["expression"]
    }
  }
}
```

### 2.3 三个关键字段

| 字段 | 作用 | 写不好会怎样 |
| --- | --- | --- |
| `name` | 工具的唯一标识 | 写错/重复，模型调不到或调错 |
| `description` | 告诉模型这工具是干嘛的 | 描述含糊，模型不知道该不该用 |
| `parameters` | 告诉模型要传什么参数 | 缺参数或类型错，模型传的参数就没法用 |

**最重要的经验**：`description` 要写得**具体、无歧义**。这是模型判断"什么时候该用这个工具"
的唯一依据。描述写得好，工具才能被正确触发。

## 三、tool_calls：模型的"调用指令"

### 3.1 结构

当模型决定调用工具时，它会在返回的 message 里附带一个 `tool_calls` 数组，每个元素长这样：

```json
{
  "id": "call_abc123",
  "type": "function",
  "function": {
    "name": "calculator",
    "arguments": "{\"expression\":\"(1+2)*3\"}"
  }
}
```

### 3.2 arguments 是 JSON 字符串，不是对象

这是最容易被忽略、也最容易踩坑的一点：`arguments` 字段**是一个字符串**，内容才是 JSON。
所以代码里必须：

```js
const args = JSON.parse(call.function.arguments);  // 字符串 → 对象
```

如果忘了 `JSON.parse`，直接把字符串传给函数，就会出现"参数是一个字符串而不是对象"的诡异错误。

## 四、结果回填：role: tool

### 4.1 回填格式

工具执行完，代码要把结果以一条特殊消息加回上下文：

```js
messages.push({
    role: 'tool',                    // 角色是 tool，不是 user/assistant
    tool_call_id: call.id,           // 必须对应上模型的调用 id
    content: result,                 // 工具返回的内容（字符串）
});
```

### 4.2 tool_call_id 必须一一对应

模型调用工具时给了 `id`，回填结果时必须带着**同一个 id**。模型靠这个 id 来匹配
"这条结果是哪次调用的结果"。如果 id 对不上，模型就不知道这条结果是回答它哪个问题的，
会乱套。

---

## 五、完整的数据流

把上面几部分串起来，一次完整的函数调用流程是：

```text
1. 请求：把 toolSchemas（工具清单）和 messages 一起发给模型
        ↓
2. 模型返回：message.tool_calls = [{ id, function: { name, arguments } }]
        ↓
3. 代码解析：name = call.function.name；args = JSON.parse(call.function.arguments)
        ↓
4. 代码执行：result = await toolHandlers[name](args)
        ↓
5. 回填：messages.push({ role: 'tool', tool_call_id: call.id, content: result })
        ↓
6. 再次请求：把更新后的 messages 发回模型，进入下一轮
```

## 六、常见坑

### 6.1 arguments 不是对象是字符串
忘记 `JSON.parse`，导致参数类型错误。**永远记得解析 arguments**。

### 6.2 id 错位
并行执行多个工具时，如果结果的顺序乱了、但 id 也一起乱了，模型会张冠李戴。
所以回填时**结果要和 id 绑定**，不能只靠数组顺序。

### 6.3 模型传了 schema 之外的参数
模型偶尔会自作主张传多余参数，或者 `required` 里的参数不传。代码侧要**做防御**：
参数缺了给默认值，参数多了忽略或报错。

### 6.4 模型的 arguments 是非法 JSON
模型生成 JSON 时偶尔会出错（少了引号、多了逗号）。所以 `JSON.parse` 要包在 try/catch 里，
解析失败时返回友好错误，而不是让程序崩溃。

## 七、代码对应关系

| 概念 | 你的项目 |
| --- | --- |
| 工具清单 | `src/tools.js` 的 `toolSchemas` 数组 |
| 工具实现 | `src/tools.js` 的 `toolHandlers` 对象 |
| 解析调用指令 | `src/agent.js` 里 `call.function.name` / `call.function.arguments` |
| 执行工具 | `src/tools.js` 的 `runTool(name, argsJson)` |
| 解析 arguments | `runTool` 里的 `JSON.parse(argsJson)` |
| 结果回填 | `src/agent.js` 里 `messages.push({ role: 'tool', ... })` |

---

## 八、小结

- 函数调用协议 = 模型和代码之间的"菜单"约定
- tool schema 告诉模型有哪些工具、每个要什么参数；description 是灵魂
- tool_calls 是模型的调用指令，arguments 是 JSON **字符串**，要用 JSON.parse 解析
- 结果回填时 role 必须是 tool，且 tool_call_id 必须和调用一一对应
- 代码侧要对模型的输出做防御（参数缺失、非法 JSON）
