# 04 · 上下文与消息管理

> 前三篇讲了 Agent 的"大脑、手脚、循环、语言"。这一篇讲"记忆"——模型是怎么记住对话的？
> 上下文是什么？太长又会怎样？这是决定 Agent 好不好用的关键一环。

---

## 一、什么是上下文

### 1.1 定义

**上下文（Context）** 就是每次调用模型时，你发给它的**全部消息内容**。模型是"无状态"的——
它自己不会记住上一轮说了啥。你问它第二句时，它之所以还记得第一句，是因为你把第一句**又发了一遍**。

### 1.2 上下文从哪来

上下文通常由这几部分组成：

- **系统提示（system）**：给模型定角色、定规则
- **历史对话**：之前所有的 user 和 assistant 消息
- **工具结果**：每轮调用工具后回填的 tool 消息

一句话：**模型的"记忆"，本质是你每次请求里完整重发的消息列表。**

---

## 二、消息的角色（role）

每条消息都有一个 `role`，它告诉模型"这条消息是谁说的"。主要有四种：

| role | 谁说的 | 作用 |
| --- | --- | --- |
| `system` | 开发者 | 定规则、定人设，通常放最前面 |
| `user` | 用户 | 用户的提问 |
| `assistant` | 模型 | 模型之前的回答（含工具调用指令） |
| `tool` | 代码 | 工具执行的结果 |

### 2.1 system 消息

只出现一次，放在消息列表最前面。它是最重要的消息，因为它决定了模型"是个什么人、守什么规矩"。

### 2.2 user 消息

用户的每次提问。注意：用户可能连续问多个问题，它们都是 user 消息。

### 2.3 assistant 消息

模型之前的回答。它必须完整保留，模型才能"知道我之前说过什么"。如果 assistant 消息里带了
`tool_calls`，也要原样保留，否则模型会"失忆"。

### 2.4 tool 消息

工具执行结果，必须带 `tool_call_id`，和对应的 assistant 工具调用一一对应。

---

## 三、system prompt 的写法

### 3.1 作用

system prompt 是给模型"立规矩"。一个 Agent 能不能老老实实调工具、不编造，很大程度上取决于
system prompt 写得清不清楚。

### 3.2 一个真实示例

下面这段来自实际项目：

```text
你是一个能使用工具的智能助手。
规则：
1. 需要真实信息（时间、文件内容、计算结果）时必须调用工具，不要凭空编造。
2. 一次可以调用多个工具，也可以分多轮调用，一步步把任务做完。
3. 任务全部完成后，用简洁的中文告诉用户你做了什么。
```

### 3.3 写好的原则

- **明确边界**：告诉模型"什么情况下必须调工具"，例如"涉及实时信息时不要编"
- **明确流程**：告诉模型"可以多轮、可以并行"
- **明确输出要求**：告诉模型"最后用简洁中文汇报"
- **别写太满**：规则太多反而会稀释重点，3~5 条关键规则往往比 20 条有效

---

## 四、token 窗口

### 4.1 什么是 token

token 是模型处理文本的最小单位，可以粗略理解为"字词片段"。一个汉字通常 1~2 个 token，
一个英文单词通常 1~2 个 token。**上下文越长，token 越多，成本越高。**

### 4.2 窗口限制

每个模型都有一个**最大上下文长度**（context window），例如 4K、8K、32K、128K token。
超过这个限制，请求会被直接拒绝，或者更糟——模型会"忘记"最早的内容。

### 4.3 超限的后果

- 请求直接报错（模型拒绝处理）
- 模型"遗忘"窗口之外的最早消息
- 费用上升、响应变慢

所以上下文管理，本质是**在有限窗口里装下最有用的信息**。

---

## 五、上下文太长怎么办

### 5.1 截断（Truncation）

最简单粗暴：只保留最近的 N 条消息，老的丢掉。

- 优点：实现简单
- 缺点：会丢失早期重要信息，可能让模型"忘了任务的初衷"

### 5.2 摘要（Summarization）

让模型把早期对话总结成一段摘要，用摘要替代原文。

- 优点：保留信息精华，省 token
- 缺点：摘要可能丢失细节，且本身要额外消耗一次模型调用

### 5.3 滑动窗口（Sliding Window）

保留最近的完整对话 + 更早的摘要，滚动前进。

- 优点：兼顾近期细节和远期梗概
- 缺点：实现复杂一些

### 5.4 上下文压缩 / 检索增强

更高级的做法是"按需取用"：把历史存到外部，当前问题时只检索**最相关的片段**塞进上下文。
这就是 **RAG（检索增强生成）** 的核心思想——不把全部资料塞进窗口，而是"用到什么取什么"。

> 这也是这套知识库存在的意义：后续学习 RAG 时，你会亲手实现"从一堆文档里检索出最相关片段，
> 再喂给模型"的过程。

## 六、多轮对话的维护

### 6.1 messages 数组

在代码里，上下文就是一个数组：

```js
let messages = [{ role: 'system', content: SYSTEM_PROMPT }];

// 用户提问
messages.push({ role: 'user', content: input });

// 模型回答（含可能的 tool_calls）
messages.push(assistantMsg);

// 工具结果
messages.push({ role: 'tool', tool_call_id: call.id, content: result });
```

### 6.2 失败回滚

如果某一轮调用失败（比如网络错误），**不能把"半截对话"留在数组里**。否则下次请求时，
上下文里会有一条"用户问了问题，但模型没回答"的断头消息，模型会困惑。

正确的做法是：记下本轮开始前的数组长度，失败时把多出来的部分裁掉：

```js
const before = messages.length;
try {
    await runAgent(input, messages);
} catch (err) {
    messages.length = before;  // 回滚：只保留到提问之前
}
```

## 七、代码对应关系

| 概念 | 你的项目 |
| --- | --- |
| system prompt | `src/agent.js` 的 `SYSTEM_PROMPT` |
| 消息数组 | `src/main.js` 的 `messages` |
| 四种 role | `messages` 里每条消息的 `role` 字段 |
| 结果回填 | `src/agent.js` 里 `messages.push({ role: 'tool', ... })` |
| 失败回滚 | `main.js` 里的 `messages.length = before` |

---

## 八、小结

- 模型是"无状态"的，记忆靠你每次重发完整消息列表
- 四种角色：system（定规则）、user（提问）、assistant（回答）、tool（工具结果）
- system prompt 要写清边界、流程、输出要求
- token 窗口有限，超限会报错或遗忘，所以需要截断/摘要/检索等策略
- 失败时要回滚上下文，别留下"断头消息"
