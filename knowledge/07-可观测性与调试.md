# 07 · 可观测性与调试

> Agent 是多轮、多工具、和外部模型交互的复杂系统，出了问题很难一眼看出原因。这一篇讲
> 怎么给 Agent 装上"黑匣子"，让每一步都可追踪、可回放、可分析成本。

---

## 一、为什么需要可观测性

### 1.1 黑盒问题

Agent 的运行过程是个黑盒：你只看到"输入问题 → 输出回答"，中间模型调了哪个工具、每轮
花了多少 token、哪里卡住了，全都看不见。一旦回答错了，你根本不知道是模型判断错了、工具
返回错了、还是网络重试了三次。

### 1.2 什么是可观测性

**可观测性（Observability）** 就是让系统内部状态对外可见。对 Agent 来说，最朴素的做法是：
**把每一轮的关键事件记录下来**。有了记录，出问题就能"回放"整个过程。

---

## 二、日志与 trace

### 2.1 记录什么

每个关键节点都应该记一条事件：

- 每轮开始（第几轮）
- 模型调用完成（耗时、token 用量、是否要调工具）
- 每个工具开始执行（工具名、参数）
- 每个工具执行结束（成功/失败、耗时、结果）
- 重试（第几次、等待多久、错误信息）
- 最终结束（总耗时、总统计）

### 2.2 JSONL 轨迹

把事件写成 **JSONL**（每行一个 JSON 对象）是最实用的方式：

```json
{"ts":"2026-11-11T10:00:00Z","type":"turn_start","turn":1}
{"ts":"2026-11-11T10:00:01Z","type":"model_done","turn":1,"ms":1567,"toolCallCount":2}
{"ts":"2026-11-11T10:00:01Z","type":"tool_start","name":"get_current_time","args":"{}"}
{"ts":"2026-11-11T10:00:01Z","type":"tool_end","name":"get_current_time","ok":true,"ms":2,"result":"14:30:00"}
{"ts":"2026-11-11T10:00:02Z","type":"final","stats":{"turns":2,"toolCalls":2}}
```

每行一个事件，方便用工具分析、搜索、回放。相比"一行行 console.log"，JSONL 结构化、可查询。

### 2.3 注意：结果要截断

工具结果可能是整个文件或整个网页，原样写进日志会把日志撑爆。写日志时**对超长字符串截断**：

```js
if (typeof value === 'string' && value.length > 2000) {
    return value.slice(0, 2000) + '…（截断）';
}
```

## 三、token 统计

### 3.1 为什么统计

token 直接关系到**钱**。每次调模型都消耗 token，不统计就不知道钱花在哪、哪轮最烧钱。

### 3.2 统计什么

模型返回的 `usage` 里通常有：

- `prompt_tokens`：输入消耗（你的问题 + 上下文）
- `completion_tokens`：输出消耗（模型的回答）
- `total_tokens`：两者之和

把每一轮的 usage **累加**起来，就是本次会话的总消耗。

### 3.3 缓存命中

DeepSeek 等模型还会返回 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`：

- 缓存命中：这部分输入复用了上次的缓存，**价格便宜很多**
- 缓存未命中：正常计费

统计缓存命中，能帮你理解"为什么同样的问题第二次问更便宜"。

---

## 四、事件回放

有了 trace 日志，出问题时就能"回放"：

1. 找到那次出错的日志文件
2. 按时间顺序读事件，看模型每轮做了什么
3. 定位是"模型选错了工具"还是"工具返回了错结果"
4. 针对性地修

这是从"瞎猜"到"有据可查"的关键一步。**先能看见，才能修对。**

---

## 五、调试技巧

### 5.1 打印关键节点

临时在关键位置打印，观察数据流：

- 模型返回的 `tool_calls` 长什么样
- 工具收到的参数对不对
- 工具返回的结果对不对

### 5.2 用最小用例复现

不要用"完整复杂问题"去调试，先用**最小可复现用例**：

- 想测工具，就直接调用工具函数，不走整个 Agent
- 想测 Agent 循环，就用假模型（mock）注入，不调真实 API

### 5.3 看 error message

错误信息是最好的线索。别一看到报错就懵，**逐字读**：

- 是网络错误（重试类）还是业务错误（参数类）？
- 状态码是什么（401/429/500）？
- 错误里有没有提示具体哪个字段有问题？

## 六、代码对应关系

| 概念 | 你的项目 |
| --- | --- |
| 轨迹日志 | `src/trace.js` 的 `createTrace`（JSONL 写入 logs/） |
| token 统计 | `src/usage.js` 的 `addUsage` / `formatUsage` |
| 事件记录 | `src/agent.js` 里的 `emit(...)` 事件 |
| 截断保护 | `src/trace.js` 里的超长字符串截断 |

> 说明：当前项目的 `trace.js`、`usage.js` 在后续重构中才会引入，本文先建立概念。

---

## 七、小结

- 可观测性 = 让 Agent 内部状态可见，最朴素的做法是记录事件日志
- JSONL 轨迹（每行一个事件）结构化、可查询、可回放
- token 统计直接关系到成本，要累加每轮的 usage
- 缓存命中 token 更便宜，值得单独统计
- 写日志时对超长字符串截断，防止日志爆炸
- 调试三板斧：打印关键节点、最小用例复现、逐字读错误信息
