# 06 · 安全与沙箱

> Agent 最危险的地方在于：模型可以读写文件、访问网络。如果代码不设边界，模型就可能
> "越权"干坏事——比如读到你电脑里的密钥、删掉关键文件、访问内网服务。这一篇讲怎么设防。

---

## 一、为什么 Agent 有安全问题

### 1.1 模型会"越权"

模型不是坏，而是"不知道边界"。它收到用户指令，会尽量照做。如果代码没限制，用户说
"读一下 `C:\Windows\System32\...`"，模型就会调 `read_file` 去读，工具如果照单执行，就出事了。

### 1.2 工具是"危险权限"

工具的能力越大，风险越大：

- `read_file`：能读任意文件 → 可能泄露敏感信息
- `write_file`：能写任意文件 → 可能破坏系统
- `delete_file`：能删任意文件 → 可能造成不可逆损失
- `fetch_webpage`：能访问任意网址 → 可能被用于攻击内网（SSRF）

所以工具层必须**内建安全约束**，不能假设模型会"自觉"。

## 二、路径沙箱

### 2.1 问题

文件工具应该只允许访问"项目目录内"的文件。但模型（或被诱导的模型）可能传入 `../`、
绝对路径、甚至"同前缀的兄弟目录"来逃出项目。

### 2.2 startsWith 的坑

一个经典错误是用 `startsWith` 判断路径是否在项目内：

```js
const target = path.resolve(file_path);
const root = path.resolve('.');
if (!target.startsWith(root)) {
    throw new Error('禁止写到项目目录之外');
}
```

这个写法有漏洞：假设项目是 `E:\proj`，那么 `E:\proj-evil\x.txt` 也**以 `E:\proj` 开头**，
会被误判为"在项目内"，从而放行。这就是"同前缀兄弟目录"绕过。

### 2.3 正确做法：path.relative

用 `path.relative` 计算相对路径，再判断结果是否"跳出"：

```js
function isInsideRoot(root, target) {
    const rel = path.relative(root, target);
    return rel === '' || (!rel.startsWith('..') && !path.isAbsolute(rel));
}
```

- 如果相对路径是 `..` 开头，说明目标在项目外 → 拦截
- 如果相对路径是绝对路径（Windows 跨盘符时会出现），也拦截
- Windows 路径大小写不敏感，比较前要统一转小写

## 三、关键文件保护

就算文件在项目内，有些文件也不能让模型删，比如：

```js
const PROTECTED_NAMES = new Set([
    'package.json', '.env', '.gitignore',
    'agent.js', 'llm.js', 'tools.js', 'main.js', 'config.js',
]);
```

`delete_file` 工具在删除前，先检查文件名是否在保护名单里，命中就拒绝：

```js
if (PROTECTED_NAMES.has(path.basename(target))) {
    throw new Error('这是一个项目关键文件，禁止删除');
}
```

原则：**宁可误伤，不可误删**。关键文件（配置、密钥、源码）必须进黑名单。

## 四、SSRF 拦截

### 4.1 什么是 SSRF

**SSRF（Server-Side Request Forgery，服务端请求伪造）**：攻击者诱导服务器去访问它本不该
访问的地址。在 Agent 场景里，`fetch_webpage` 工具如果允许访问任意网址，模型可能被诱导去
访问 `http://localhost:3306`、`http://192.168.1.1` 这类内网地址，探测内网服务。

### 4.2 内网地址拦截

在发起网页请求前，先检查主机名是否属于内网/本机：

```js
function assertPublicHost(hostname) {
    const host = hostname.toLowerCase();
    const blocked =
        host === 'localhost' ||
        host === '0.0.0.0' ||
        host === '::1' ||
        /^127\./.test(host) ||      // 回环地址
        /^10\./.test(host) ||       // 内网 A 类
        /^192\.168\./.test(host) || // 内网 C 类
        /^169\.254\./.test(host);   // 链路本地
    if (blocked) {
        throw new Error('禁止访问内网或本机地址');
    }
}
```

> 注意：这只是"主机名粗筛"，并不能完全防住 DNS rebinding 等高级攻击。生产环境需要更严格的
> 防护，但作为教学项目，这一层已经足够理解"工具权限边界"的概念。

## 五、计算器白名单（防代码注入）

计算器工具用 `new Function` 执行表达式，如果直接执行用户输入，等于"把任意字符串当代码跑"，
这是经典的代码注入漏洞。必须做**白名单校验**：

```js
// 只允许数字和 + - * / ( ) . 和空格
if (!/^[\d\s+\-*/().]+$/.test(expression)) {
    throw new Error('只支持数字和 + - * / ( )');
}
const result = new Function(`return (${expression})`)();
```

- 白名单 = 只允许明确合法的字符，其余一律拒绝
- 黑名单（列出非法字符）容易漏，白名单更安全

---

## 六、最小权限原则

安全设计的核心思想是**最小权限**：

1. **默认拒绝**：工具默认只能碰最小范围，需要更大权限再显式开放
2. **能只读就不写**：`read_file` 不提供写能力
3. **能白名单就不黑名单**：列"允许什么"比列"禁止什么"更可靠
4. **结果也截断**：读文件、抓网页都限制长度，防止把超大内容塞进上下文

## 八、小结

- Agent 的危险来自"模型没边界意识 + 工具权限大"，所以工具层必须内建安全约束
- 路径沙箱：用 `path.relative` 判断，别用有漏洞的 `startsWith`
- 关键文件（配置、密钥、源码）进删除黑名单
- SSRF：访问网页前拦截内网/本机地址
- 计算器等"执行类"工具，必须做白名单校验防注入
- 核心思想是"最小权限"：默认拒绝，按需开放
