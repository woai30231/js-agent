# 01 · Agent 基础概念

> 这是理解整个 Agent 开发体系的起点。本文回答三个最根本的问题：Agent 到底是什么？它和普通的
> 大模型（LLM）有什么区别？一个 Agent 由哪几部分组成？

---

## 一、什么是 Agent

### 1.1 定义

**Agent（智能体）** 是一个以大语言模型（LLM）为核心，能够**自主规划、调用工具、多步执行**，
最终完成一个复杂任务的系统。

关键在于"自主"两个字。普通聊天机器人只会"回答一句话"；而 Agent 会自己判断"要完成这个任务，
我需要分几步、每一步该调什么工具"，然后一步步把任务做完。

### 1.2 一个通俗的类比

把 LLM 想象成一个"很聪明但手脚被绑住的大脑"：

- 它能思考、能推理、能写方案，但它**不能上网、不能读文件、不能算数、不能查时间**。
- 普通聊天机器人 = 这个大脑，你问它答，它只能用"记忆里背过的知识"回答。
- Agent = 给这个大脑装上了"手脚"（工具）和一个"执行计划"（循环），于是它能：
  1. 决定去查一下实时时间
  2. 调用"查时间"这个工具拿到结果
  3. 把结果组织成回答还给你

### 1.3 Agent 的三个核心特征

1. **能调用工具**：超出模型记忆范围的事，通过工具去完成
2. **能多步执行**：不是一问一答，而是"思考 → 行动 → 观察 → 再思考"的循环
3. **能根据反馈调整**：工具失败或结果不对时，换参数、换思路再来

---

## 二、Agent 与普通 LLM 的区别

### 2.1 普通聊天机器人的局限

一个只接 LLM 的聊天机器人，面对"现在几点"这个问题会怎样？如果模型的训练数据里没有
"当前时间"，它就**只能编一个时间**，或者老实承认不知道。

这就是"幻觉"的根源之一：模型只能基于训练时的知识回答，**它没有获取实时信息的能力**。

### 2.2 Agent 多了什么

Agent 在 LLM 之上，增加了三样东西：

1. **工具清单**：告诉模型"你有哪些工具可用，每个工具能干什么、需要什么参数"
2. **执行循环**：模型输出"调用工具的指令"后，由代码真正去执行，并把结果喂回给模型
3. **上下文管理**：把多轮对话、工具结果都维护好，让模型知道"现在进行到哪一步了"

### 2.3 对比表格

| 维度 | 普通聊天机器人 | Agent |
| --- | --- | --- |
| 能否获取实时信息 | 不能 | 能（通过工具） |
| 能否读写文件 | 不能 | 能（通过工具） |
| 能否执行计算 | 只能心算，易错 | 能（调用计算器工具，精确） |
| 执行方式 | 一问一答 | 多步循环 |
| 出错处理 | 直接给错误答案 | 观察错误、调整重试 |

## 三、Agent 的四大组成

一个最小可用的 Agent，由四块拼成：

### 3.1 大脑：LLM

负责"思考"和"决策"。它接收当前上下文，输出两种可能的结果：

- 一段**最终回答**（任务完成）
- 一组**工具调用指令**（它需要更多信息，点名要调某个工具）

```text
大脑的输入：系统提示 + 对话历史 + 工具清单
大脑的输出：普通文本回答  或  工具调用指令
```

### 3.2 手脚：工具（Tools）

工具是 Agent 与外部世界交互的通道。常见的工具有：

- 获取实时信息：查时间、查天气、网页搜索
- 操作文件：读文件、写文件、删文件
- 执行计算：计算器、运行代码
- 调用外部服务：发邮件、查询数据库、调第三方 API

工具的定义通常包含两部分：**描述**（告诉模型它是干嘛的）和**实现**（代码真正怎么执行）。

### 3.3 记忆：上下文与消息历史

Agent 需要"记住"对话进行到哪了。上下文通常包含：

- **system 消息**：给模型定角色、定规则（最重要的一条）
- **历史消息**：之前的用户问题和模型回答
- **工具结果**：每次调用工具后拿到的返回

上下文不是无限的，它受 **token 窗口**限制，需要专门的策略来管理（详见第 04 篇）。

### 3.4 规划：执行循环

这是 Agent 的"发动机"，最经典的是 **ReAct 循环**（详见第 02 篇）：

```text
思考（Thought） → 行动（Action） → 观察（Observation） → 再思考 → …… → 最终回答
```

循环由代码控制，通常有一个**最大轮次上限**，防止 Agent 陷入死循环烧 token。

## 四、Agent 的工作方式：一个完整例子

假设用户问："帮我把项目里 note 目录下的文件列出来，然后统计一共有几个。"

一个 Agent 会这样运转：

### 第 1 轮
- **思考**：用户要我列目录并统计数量，我需要先列出目录
- **行动**：调用 `list_files` 工具，参数 `dir = "note"`
- **观察**：工具返回 `["a.md", "b.md", "c.md"]`

### 第 2 轮
- **思考**：拿到了 3 个文件名，统计结果是 3
- **行动**：不再调用工具，直接输出最终回答
- **最终回答**："note 目录下共有 3 个文件：a.md、b.md、c.md"

注意：整个过程模型调用了 1 次工具，循环跑了 2 轮。这就是 Agent 与"一问一答"的本质区别。

## 五、最小 Agent 的代码骨架

下面是一个极度简化、但结构完整的 Agent 伪代码，对应真实项目里的 `runAgent`：

```js
// 极简 Agent 骨架（教学用，非完整实现）
async function runAgent(question, messages) {
    // 1. 把用户问题加入上下文
    messages.push({ role: 'user', content: question });

    // 2. 进入执行循环，最多 N 轮
    for (let turn = 1; turn <= maxTurns; turn++) {
        // 3. 问模型：你是要直接回答，还是要调工具？
        const assistantMsg = await chat({ messages, tools: toolSchemas });

        // 4. 如果模型直接给了答案，返回
        if (!assistantMsg.tool_calls || assistantMsg.tool_calls.length === 0) {
            return assistantMsg.content;
        }

        // 5. 模型要调工具：逐个执行，把结果喂回上下文
        for (const call of assistantMsg.tool_calls) {
            const result = await runTool(call.function.name, call.function.arguments);
            messages.push({ role: 'tool', tool_call_id: call.id, content: result });
        }
        // 回到第 3 步，再问一次模型
    }

    return '已达到最大轮次，任务提前结束';
}
```

### 这段代码对应了你项目里的哪部分

| 骨架里的东西 | 项目里的落点 |
| --- | --- |
| `runAgent` | `src/agent.js` 的 `runAgent` 函数 |
| `chat(...)` | `src/llm.js` 的 `chat` 函数 |
| `toolSchemas` | `src/tools.js` 的 `toolSchemas` |
| `runTool` | `src/tools.js` 的 `runTool` |
| `messages` | `src/main.js` 里维护的 `messages` 数组 |
| `maxTurns` | `src/config.js` 里的 `maxTurns` |

## 六、Agent 的常见类型

### 6.1 单轮工具型
模型一次调用一个或几个工具，拿结果后直接回答。适合简单任务，是最常见的形态。

### 6.2 多轮自主型
模型在多轮循环里反复调用工具、根据中间结果调整策略。适合"帮我查资料并整理成报告"这类复杂任务。

### 6.3 多智能体协作型
多个 Agent 分工，比如一个负责规划、一个负责执行、一个负责检查。适合更大的系统，但复杂度也更高。

## 七、常见误区

### 7.1 误区一：Agent 有"意识"或"会自己思考"
Agent 的"思考"本质是模型基于上下文的概率预测输出。它没有意识，也不会真正"理解"，它只是
按照指令和上下文生成下一个 token。把它当成一个"非常会照章办事的执行者"，而不是"有主见的人"。

### 7.2 误区二：工具越多越好
工具越多，模型的选择负担越重，越容易选错。设计原则是：**够用就好，描述写清楚**。一个
含糊的工具，比没有工具更危险。

### 7.3 误区三：Agent 一定比直接调 LLM 好
如果任务只是"用一句话介绍你自己"，直接调 LLM 就够，上 Agent 纯属浪费 token 和延迟。
Agent 的价值在于**需要工具、需要多步执行**的场景，简单任务没必要。

---

## 八、小结

- Agent = LLM + 工具 + 上下文 + 执行循环
- 它与普通聊天机器人的核心区别是：**能调用工具、能多步执行、能根据反馈调整**
- 一个 Agent 的最小骨架，就是一个"问模型 → 执行工具 → 喂回结果 → 再问"的循环
- 不是所有任务都需要 Agent，简单任务直接调 LLM 即可
